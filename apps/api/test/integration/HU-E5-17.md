# HU-E5-17 · Evidencia de Vacantes

La suite HTTP usa el controlador y servicio de Vacantes de epic3, peticiones Supertest, un actor de prueba y un sustituto de Prisma en memoria. Comprueba respuestas HTTP y operaciones de persistencia. La autenticación y la concurrencia de PostgreSQL quedan fuera de esta suite.

| Criterio | Cobertura |
| --- | --- |
| CA-01 a CA-03 | Alta, segunda solicitud idempotente, perfil incompleto, vacante cerrada y pausada |
| CA-04 y CA-05 | Aislamiento HTTP con dos titulados y dos postulaciones en ambas consultas y campos públicos de la oferta |
| CA-06 | Listado y cambio de etapa con acceso a la empresa y con acceso denegado |
| CA-07 | `vacancy-matching.integration.spec.ts` invoca `POST /api/v1/affinity/batch` (modos `vacancies` y `applicants`) con controlador, caso de uso, adaptador Prisma y NLP reales sobre PostgreSQL local desechable. Incluye 403 para empresa ajena y para titulado en modo `applicants`. Opt-in con `TEST_DATABASE_URL`; falta registrar su ejecución local |
| CA-08 | Tres pares sintéticos perfil-vacante y evaluador de orden relativo. `vacancy-matching-regression.spec.ts` aplica la regla real de HU-10 (100 %, 50 % y 0 %) y exige las tres comparaciones estrictas sin base de datos. La misma verificación se repite por el endpoint real en la prueba de CA-07 |
| CA-09 | Servicio de postulaciones, carga, error y reintento en la oferta, desglose ausente y habilidades recibidas |
| CA-10 a CA-12 | Comprobaciones ordinarias con APP_ENV=test. Dobles explícitos en las suites nuevas. Registrar cada defecto con criterio, caso reproducible y HU responsable |

## Integración de HU-10

`POST /api/v1/affinity/batch` exige el permiso `perfil:self:read` con rol titulado (modo `vacancies`) o `empresas:self:read` con rol empresa (modo `applicants`). La prueba siembra las entidades de `vacancyMatchingCases` con SQL directo (`support/vacancy-matching-seed.ts`) en la base temporal del helper, entrega los tres porcentajes observados a `passesMatchingRegression` y exige un resultado verdadero.

Para ejecutarla, con un PostgreSQL local (nunca una base oficial):

```
TEST_DATABASE_URL=postgres://postgres:clave@127.0.0.1:5432/postgres pnpm --filter api test:integration -- vacancy-matching
```

El endpoint por lote solo calcula y responde; no escribe `porcentaje_match`. Ese dato se guarda al postular, en `VacantesService`, y el e2e `vacantes-hu-e5-17.e2e.spec.ts` comprueba que porcentaje y fecha se guardan juntos o ambos nulos (restricción `postulacion_match_fecha_pareados`).

Para reproducir los controles ordinarios, usar Node 22.22.1, pnpm 9, APP_ENV=test y ejecutar pnpm lint, pnpm test y pnpm build desde la raíz. Los resultados de la ejecución se registran en la PR.
