## Integración de HU-10

`POST /api/v1/affinity/batch` exige el permiso `perfil:self:read` con rol titulado (modo `vacancies`) o `empresas:self:read` con rol empresa (modo `applicants`). La prueba siembra las entidades de `vacancyMatchingCases` con SQL directo (`support/vacancy-matching-seed.ts`) en la base temporal del helper, entrega los tres porcentajes observados a `passesMatchingRegression` y exige un resultado verdadero.

Para ejecutarla, con un PostgreSQL local (nunca una base oficial):

```
pnpm --filter api exec jest --config jest.integration.config.cjs --runInBand --runTestsByPath test/vacancy-matching.integration.spec.ts
```

El endpoint por lote solo calcula y responde; no escribe `porcentaje_match`. Ese dato se guarda al postular, en `VacantesService`, y el e2e `vacantes-hu-e5-17.e2e.spec.ts` comprueba que porcentaje y fecha se guardan juntos o ambos nulos (restricción `postulacion_match_fecha_pareados`).

Antes de ejecutar Jest, definir `APP_ENV=test` y apuntar `TEST_DATABASE_URL`, `DATABASE_URL` y `DIRECT_URL` al contenedor local. La verificación utilizó el puerto 54329 y el contenedor se retiró al terminar.

- **CA-06, pendiente de decisión del responsable de Vacantes/Postulantes**. Desde una empresa ajena, solicitar el listado de postulantes devuelve 404. El cambio de etapa devuelve 403. El criterio de planificación pide 403 para el acceso denegado. El e2e reproduce ambas respuestas en `vacantes-hu-e5-17.e2e.spec.ts`. Confirmar si ocultar la existencia de la vacante con 404 es el contrato esperado.

Para reproducir los controles ordinarios, usar Node 22.22.1, pnpm 9, APP_ENV=test y ejecutar pnpm lint, pnpm test y pnpm build desde la raíz. Los resultados de la ejecución se registran en la PR.
